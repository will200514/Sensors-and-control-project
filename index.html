Abstract

A TurtleBot3 Burger in a MuJoCo room with randomly placed obstacles has to find a charging station marked with a single ArUco marker (ID 1, DICT_4X4_50) and dock in front of it. The robot is not told its start pose, the dock position or the obstacle positions. It rotates on the spot until the camera detects the marker, uses that first detection to define a dock-centred frame, then plans a path through a LiDAR occupancy grid and drives to a stopping point 0.30 m in front of the marker.

The state is the planar pose [x, y, theta]. An extended Kalman filter predicts with a unicycle model driven by wheel-encoder odometry and corrects with full-pose measurements recovered from the marker's four corners using PnP. A time-varying LQR controller, designed on the linearised tracking-error model, tracks the planned path using the EKF estimate only. Simulator ground truth is used only to score and plot results.

Model

The TurtleBot3 is modelled as a differential-drive unicycle with state x = [x, y, θ] and input u = [v, ω], where v = (vR + vL)/2 and ω = (vR − vL)/b with track width b = 0.160 m and wheel radius 0.033 m. The discrete motion model integrates a constant-(v, ω) arc over each step Δt = 0.05 s:

xk+1 = xk + vΔt·s·cos(θk + ωΔt/2),   yk+1 = yk + vΔt·s·sin(θk + ωΔt/2),   θk+1 = θk + ωΔt

with s = sin(a)/a, a = ωΔt/2, which removes the singularity at ω = 0. The Jacobians F = ∂f/∂x and G = ∂f/∂u are used by the EKF.

For control, the model is linearised about the reference trajectory in the robot-frame error e = [ex, ey, eθ] with correction input δu = [δv, δω]. The resulting (A, B) pair is discretised at 20 Hz. Controllability: the error model is controllable whenever the reference speed vr ≠ 0, which is checked in the unit tests; the tracker clamps vr to at least 0.01 m/s for this reason. Observability: the camera measures the full pose (H = I3), so the state is observable whenever the marker is in view. With odometry only, the absolute pose is not observable and the error grows without bound, which the odometry-only comparison in the results shows.

Coordinate frames

D (dock frame): origin on the floor directly below the marker centre, +x out of the wall, +y along the wall, +z up. It is created at the first accepted marker detection. R (robot frame): x forward, y left, z up; the EKF estimates the pose of R in D. C (camera frame): OpenCV convention, x right, y down, z forward, mounted 0.06 m ahead of and 0.12 m above the robot origin. Before acquisition the EKF runs in a frame defined by the robot's start pose; at acquisition the map is discarded and rebuilt in D. The docking target is [0.30, 0, π] in D, which is a marker-relative offset, not a room coordinate.

Sensing

  • Camera: 640x480 at 10 Hz, fx = 530 px, principal point (320, 240), zero distortion in simulation. Only marker ID 1 is accepted. Square-marker PnP gives candidate poses, then an upright-marker, level-robot fit picks the one with the lowest reprojection error (rejected above 2.0 px).
  • Measurement covariance: the corner-fit Jacobian maps an assumed corner noise of 1.0 px into a full 3x3 pose covariance, with floors of 1.5 cm and 1.0° for calibration and model error, then scaled by r_scale = 2.0. Near-ambiguous fits inflate the covariance.
  • Wheel encoders: 20 Hz, speed noise 0.003 m/s, 2% per-step slip and up to 1% per-trial bias.
  • LiDAR: 120 beams, 3.5 m range, σ = 0.01 m, at 5 Hz. Used for the occupancy grid only.

Disturbed run (seed 1003, 6 N push at 12 s)

The hardest of the 20 push trials. The push is not in the motion model, so the heading estimate is knocked about 35° off while the filter still reports a tight covariance (NEES above 100). With the marker out of view between 22 s and 45 s nothing can correct it. The innovation gate then rejects the first camera fixes as outliers (21 rejected), and the lock-out recovery re-opens the gate (4 times) until the estimate snaps back. The robot still docks at 56 s with 2.6 cm error.

Real hardware

The same pipeline (EKF, planner, LQR and docking logic) runs on a real TurtleBot3 through the UTS-RI turtlebot_rosbridge package (code in track A - hardware/). Below is a full real-robot run: the robot searches for the marker, plans around the obstacles using the LiDAR, and docks in front of the ArUco marker.

Real TurtleBot3 docking run, 2 November 2026 (98 s).

  • Camera calibration: 50 checkerboard views, RMS reprojection error 0.645 px, fx = 1170 px, fy = 1171 px at 640x480. The simulated camera uses fx = 530 px, so the real lens is much narrower.
  • Geometry, measured on the robot: 0.10 m marker centred 0.15 m above the floor, camera 0.15 m high and 0.06 m forward, pitched down 3.7°.
  • Logged run (103 s): search 0–11 s, marker confirmed at 11 s, navigation with a LiDAR back-off near an obstacle (39–47 s), marker reacquired, then visual servoing and final alignment. The log ends in the align phase with the estimate 3.6 cm short of the target and 4.4 cm to the side, heading about 1° off.

Limits: there was no motion capture, so we can only compare the estimate with the target, not true pose error, and we have one logged run rather than a set of trials. Hardware needed extra behaviour that simulation did not (back-off from close obstacles, reacquire and visual servo before final alignment) because real wheel slip and the narrow camera FOV lose the marker more often.

Results discussion and reflection

Accuracy. All 40 trials docked. The final error clusters tightly between 2.2 and 3.9 cm because the controller stops once the estimate is within 2.5 cm of the target, and the EKF's own error at that point adds to it. Tightening the stop tolerance would cut the final error but lengthen the run.

Estimation. Fusing the camera cuts position RMSE from 16.5 cm (odometry only, same initial fix) to 3.0 cm. In the nominal case median NEES is 1.09 and 88% of samples sit inside the 95% bound of 7.81, so the filter is consistent to slightly conservative. The camera floors (1.5 cm, 1°) and r_scale = 2 make R larger than the raw corner-noise model, which is why NEES sits below 3.

Disturbance. The push still docks every time, but costs 7.6 s on average and doubles the RMSE. The cause is in the estimator, not the controller: the push is unmodelled, so Q is too small right after it and the filter is overconfident (per-trial mean NEES 10–135). The 99% gate then rejects good camera fixes, and recovery depends on the lock-out logic (0.95 lock-out recoveries per trial under push against 0.15 nominal). A fix would be to inflate Q when wheel commands and measured motion disagree.

Limitations. The robot searches by rotating on the spot, so a fully occluded marker is never found and the run times out after 40 s; the scene generator keeps a line of sight to the marker for this reason. Wheel bias is not estimated. The ablation and LQR sweeps above come from an earlier design iteration and should be rerun on the final code.
